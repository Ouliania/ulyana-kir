# workflow
- When making product/structure decisions for the website, frame analysis around marketing and client intent — what different customer segments search for, their psychological triggers, and what converts at each stage of the funnel. Confidence: 0.80
- Get design approval from the user before implementing major visual changes — do not commit to a full redesign without showing the plan first. Confidence: 0.85
- When a plan has numbered phases, follow the specified order — do not skip to a later phase without confirming. Confidence: 0.70
- Do not modify sections/blocks the user hasn't asked to change — if the user didn't include a section in the scope, leave it alone. Confidence: 0.70
- Drafts marketing copy in Russian first; expects the assistant to produce the English equivalent once the Russian is settled. Confidence: 0.85
- Expects the assistant to polish rough-draft copy — fix grammar, typos, punctuation, and offer refined alternative phrasings — without being explicitly asked. Confidence: 0.75
- Cares about image file size and page performance — proactively flags heavy assets and expects optimization (e.g., compressing 1.9MB webp down to 200–400KB). Confidence: 0.80
- Image compression must be quality-gated — optimize only when there is no visible quality loss. Use objective metrics (PSNR ≥ 38 dB) to verify before replacing originals. Confidence: 0.80
- Prefers separate, task-scoped git commits — each logical change gets its own commit so nothing gets mixed up. Exclude unrelated changes (taste files, other cleanup) from the commit; they can be committed separately or merged later. Confidence: 0.80
- Distinct workstreams belong on separate feature branches — do not mix unrelated changes (e.g., visuals vs. copy) on the same branch. Branch naming: `feature/{descriptive-slug}`. Confidence: 0.80
- When a design is generated via Superdesign (or similar tools), the code implementation must follow in the same session — do not leave designs as unapplied mockups. The user expects to see the visual result in the browser, not just a generated HTML draft. Confidence: 0.80
- When multiple design variants/options are presented, the assistant must implement the exact variant the user explicitly selected — confusing variants (e.g., implementing "with accent lines" when the user chose "Modern Cinematic") is a critical error. Double-check which variant was chosen before writing code. Confidence: 0.85
- Prefers delegating specialized analytical domains (marketing strategy, UX critique, etc.) to dedicated CommandCode agents rather than handling everything through the general assistant. Each agent should be scoped to a single function and respect project taste conventions. Confidence: 0.70
- When requesting audits or critiques, prefers quick, high-signal findings (3–5 items) over exhaustive analysis. Tone should be constructive and grounded, not harsh or tearing apart — focus on what actually moves the needle. Confidence: 0.65
- When project constraints are locked in during conversation (e.g., marketing voice, CTA architecture, design rules), proactively sync them into the relevant CommandCode agent configuration files. Also proactively give agents the tools they need for their domain (e.g., shell_command for curl when an agent needs to check the live site). Confidence: 0.75
- Maintains personal skill drafts in `~/ULYANAWEB/Skills-mine/` as raw markdown files, then asks the assistant to formalize them into proper `.commandcode/skills/{name}/SKILL.md` structures — adapting to the CommandCode SKILL.md format, adding YAML frontmatter, and linking to relevant project agents where appropriate. Confidence: 0.80
- Communication: skip greetings, pleasantries, and conversational filler. Write concisely, clearly, and to the point — the user values signal density over social niceties. Confidence: 0.70
